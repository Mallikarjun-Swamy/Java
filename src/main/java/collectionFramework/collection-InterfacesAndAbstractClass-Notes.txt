 1️⃣ Iterable (interface):

        🔹 What is Iterable?
           Iterable is the root interface that allows an object to be iterated using a loop.

           1. What problem the interface solves?
               The primary problem Iterable solves is providing a standardized contract for
               sequential access to elements within a collection of objects.

               It abstracts the mechanism of iteration away from the specific internal
               structure (like an array, a linked list, or a hash table) of the collection.

               It enables the use of the Enhanced for Loop (or "for-each loop") in Java,  which simplifies
               code significantly. Any object that implements Iterable can be used in a for-each loop.

           2. How operations work (the core method)
               The Iterable interface has one abstract method (until Java 8):
                   Iterator<T> iterator(): This method returns an Iterator object,
                   which is responsible for traversing the elements.

                   Note on Iterator: The Iterator interface has three key methods:
                        1. boolean hasNext(): Returns true if there are more elements.
                        2. E next(): Returns the next element in the iteration.
                        3. void remove(): Removes the last element returned by next() (optional operation).

               In Java 8, two default methods were added:

               default void forEach(Consumer<? super T> action):
                    Enables iterating over elements using a lambda expression or method reference.

               default Spliterator<T> spliterator():
                    Used primarily to support parallel processing in the Stream API.

           3.Real interview notes
               Question: "What is the difference between Iterable and Iterator?"

               Answer: Iterable is an interface implemented by a Collection;
                       it has the iterator() method and makes the collection eligible for the for-each loop.

                       Iterator is an interface used to traverse the collection;
                       it has the methods hasNext(), next(), and remove().

               Question: "Why does the Collection Framework start with Iterable and not Collection?"

               Answer: Because the most fundamental requirement for anything to be considered a 'collection' in Java is the ability to iterate over its elements. Iterable defines this most basic contract.

           4.Common misconceptions
               Misconception: You must use an Iterator for all loops.

               Correction: The enhanced for-each loop is the syntactic sugar built on top of the Iterator interface.
               You only need to explicitly use an Iterator if you need to safely remove elements during the iteration
               or if you are iterating over a structure that doesn't support the for-each loop

           5. The Core Relationship: Producer-Consumer
               The entire Collections Framework relies on this two-part  contract:
               Interface                                         Role (What it Is)                                   Core Responsibility (What it Does)
               Iterable<T> (present in lang pkg)                The Producer (or the Structure)                 Produces an Iterator.
               Iterator<T> (present in util pkg)                The Consumer (or the Traversal Mechanism)       Consumes the Iterable's elements.1.

               Iterable Produces the Iterator:
                     The Iterable interface defines only one abstract method: Iterator<T> iterator();

                     The Contract: Any class (like ArrayList, HashSet, or your custom collection) that implements
                     Iterable must provide an implementation for iterator().

               The Result: When you call myList.iterator(), the myList object (which is an Iterable) executes
                           its iterator() method and returns a brand new Iterator object.

               Iterator Maintains State for Traversal:
                    The Iterator object is a helper class that is distinct from the collection itself.

               Its primary job is to keep track of the current position (the state of the iteration).
                   It provides the methods needed to move through the collection:
                       hasNext(): Checks if there is another element.
                       next(): Retrieves the current element and advances the position.
                       remove(): Removes the element last returned by next().

               Mechanism: How the Iterator Object is Returned
                   This sequence explains the roles of the main class, the inner class,
                   and the interfaces to produce the Iterator object.

                   1. The Contract (Interface Iterable)
                      The Collection interface (and thus all its children like List, Set, etc.) extends Iterable.
                      This forces any concrete collection class to provide an implementation for the iterator() method.

                   2. The Main Class's Role
                      The Main Collection Class (e.g., ArrayList) implements the List interface
                      (which requires the iterator() method since it is implementing Iterable).

                      The implementation of this method looks like this:
                              public Iterator<E> iterator() {
                                    return new Itr();
                              }

                   Crucially, the main class is the factory: it is responsible for creating and returning the Iterator object.

                   3. The Inner Class's Role
                      A Private Inner Class (conventionally named Itr in many Java collections)
                      is defined inside the main collection class.

                      This inner class implements the Iterator interface
                      (i.e., it provides the concrete logic for hasNext(), next(), and remove()).

                      Because it's an inner class, it has direct access to the main collection's private data structure
                      (the array in ArrayList, the nodes in LinkedList).

                   4. The Return Flow (Creating the Object)
                       When a user calls list.iterator(), the ArrayList object executes its iterator() method.
                       This method calls new Itr(), which instantiates the private inner class.

                       The method then returns the reference to this newly created Itr object.

                       Since Itr implements Iterator, the return type matches the required Iterator<E> interface.



 2️⃣ Collection (interface): (java.util.Collection and Introduced in 1.2):

        The Collection interface is the root of the Collection Hierarchy
        (List, Set, Queue) and defines the common behavior shared by almost all groups of objects in Java.

        1. What problem the interface solves
            The Collection interface solves the problem of providing a unified,
            top-level API for handling groups of objects (elements).

            It acts as a generalized container, defining the basic operations
            (add, remove, check size, check existence) that any group of objects must support.

            It standardizes how elements are stored and managed, regardless of whether the collection
            allows duplicates (like a List) or requires uniqueness (like a Set)

        2. Core Methods
            In Java 1.2:
                    1. boolean add(E e);
                        Adds the specified element to the collection if it is permitted.
                        Returns true if the collection changed as a result of the call.

                    2. boolean addAll(Collection<? extends E> c);
                        Adds all elements from the specified collection to this collection.
                        Returns true if at least one element was added

                    3. void clear();
                        Removes all elements from the collection. After this call, the collection is empty.

                    4. boolean contains(Object o);
                        Returns true if the collection contains an element equal to the specified object.

                    5. boolean containsAll(Collection<?> c);
                        Returns true if the collection contains all elements of the specified collection

                    6. boolean remove(Object o);
                        Removes a single instance of the specified element from the collection, if present.
                        Returns true if the collection contained the element.

                    7. boolean removeAll(Collection<?> c);
                        Removes all elements from the collection that are also contained in the specified collection.
                        Returns true if the collection changed as a result.

                    8. boolean retainAll(Collection<?> c);
                        Retains only the elements in the collection that are contained in the specified collection.
                        All other elements are removed.

                    9. int size();
                        Returns the number of elements in the collection

                    10. boolean isEmpty();
                        Returns true if the collection contains no elements.

                    11. Iterator<E> iterator();
                        Returns an iterator over the elements in the collection.

                    12. Object[] toArray();
                        Returns an array containing all elements in the collection.

                    13. <T> T[] toArray(T[] a);
                        Returns an array containing all elements in the collection,
                        stored in the specified array type if possible

                    14. boolean equals(Object o)
                    15  int hashcode()

            5 Default methods (Java 8):
                    16. default boolean removeIf(Predicate<? super E> filter);
                        Removes all elements of the collection that satisfy the given predicate.
                        Returns true if any elements were removed.

                    17. default Spliterator<E> spliterator();
                        Returns a Spliterator over the elements of the collection, which can be used
                        for sequential or parallel traversal.

                    18. default Stream<E> stream();
                        Returns a sequential Stream with this collection as its source.

                    19. default Stream<E> parallelStream();
                        Returns a possibly parallel Stream with this collection as its source.

                    20. default <T> T[] toArray()


        3. Note on Optional Operations:
                All modification methods (add, remove, addAll, clear etc.) are declared as optional operations.
                If an implementing class (like AbstractCollection) chooses not to support a method
                (e.g., in a read-only collection), it must throw an UnsupportedOperationException.

                Optional operation means: the method exists in the interface,
                but the collection may choose to reject it at runtime by throwing UnsupportedOperationException.

        4. By default, implementations of Collection are not synchronized.

            To achieve thread safety, a developer must use:

            1. Wrapper Classes: Collections.synchronizedCollection(Collection c).
                    example:
                    // 1. Create a standard, non-synchronized concrete collection.

                            Collection<String> nonSyncList = new ArrayList<>();

                    // 2. Use the static factory method to return a synchronized wrapper,
                          The returned object (syncdCollection) is now thread-safe.

                          Collection<String> syncdCollection = Collections.synchronizedCollection(nonSyncList);

            🛑 IMPORTANT Interview Note on Iteration
                A critical point for interviews:
                The wrapper synchronizedCollection() makes individual operations (like add or remove) thread-safe,
                but it DOES NOT make the iteration process thread-safe.

                If you iterate over the synchronized collection (using a for-each loop or an Iterator) in
                a multi-threaded environment, you still need to use external synchronization (a manual lock)
                around the iteration block to prevent a ConcurrentModificationException:

            2. Concurrent Implementations:
               Classes from the java.util.concurrent package (e.g., CopyOnWriteArrayList).

        5. Real interview notes
           Question: "Why doesn't Map extend Collection?"
           Answer: Because Collection deals with a single grouping of elements (objects).
                   Map deals with key-value pairs, which is a fundamentally different type of grouping,
                   hence it requires its own top-level interface.

           Question: "Explain Optional Operations." (Misconception: All methods must be implemented to modify the collection)
           Answer: These are modification methods that an implementing class can choose not to support.
                    If unsupported, the method must throw an UnsupportedOperationException.
                    This design allows for immutable/read-only collections to still be considered part of the
                    Collection framework.
                    The modification methods are optional. Read-only collections are valid implementations.

 3️⃣ AbstractCollection (Abstract Class):

        The AbstractCollection class provides a skeleton implementation of the Collection interface to minimize the
        effort required to implement a full collection.

        1. What problem the class solves
            The primary problem AbstractCollection solves is reducing boilerplate code for developers creating new,
            custom collection implementations.

            It implements several non-obvious methods of the Collection interface (isEmpty(), contains(),
            toArray(),addAll(), etc.)
            using just two fundamental ( int size() and  Iterator<E> iterator()  )
            methods that must be provided by the concrete subclass:

            By inheriting from AbstractCollection, a developer only needs to focus on the unique data structure
            logic of their new collection, not the standard utility methods.


            It is the base class for many of the major classes in the Collections Framework.

                                                    |--> AbstractList -> ArrayList, Vector etc
              Collection --> AbstractCollection --> |--> AbstractSet -> Hashset, LinkedHashset etc
                                                    |--> AbstractQueue -> PriorityQueue etc

            Why AbstractCollection exists because
                Without it: Every collection class would have to
                re-implement the following fully Implemented Methods.
                (all these method use size() and iterator() methods internally, which are abstract)

                1. public boolean isEmpty() {return size() == 0;}
                2. public boolean contains(Object o) { // logic Code }
                3. public Object[] toArray() { // logic Code }
                4  public <T> T[] toArray(T[] a) { // logic Code}
                5. public boolean add(E e) { throw new UnsupportedOperationException(); }
                6. public boolean remove(Object o) { // logic Code }

                //Bulk operations
                7. public boolean containsAll(Collection<?> c) { // logic Code }
                8. public boolean addAll(Collection<? extends E> c) { // logic Code }
                9. public boolean removeAll(Collection<?> c)  { // logic Code }
               10. public boolean retainAll(Collection<?> c) { // logic Code }
               11. public void clear() { // logic Code }
               12. public String toString() {  // logic Code }

                This causes huge code duplication in all concrete implementation classes.
                AbstractCollection solves this by providing common logic.

                Unimplemented methods:
                1. public abstract Iterator<E> iterator();
                2. public abstract int size();

                int size() and iterator are Abstract,
                While used by the others methods, these two methods must be implemented in subclasses.


 4️⃣ List (interface) : (implements SequencedCollection (I) --> Collection(I))

                Iterable<E>
                  └── Collection<E>
                        └── SequencedCollection<E>   (Java 21)
                              └── List<E>

            The List interface is the child of Collection and represents an ordered sequence of elements
            where access is primarily via an integer index (position).
            (child interface of SequencedCollection (I))


                1. What problem the List interface solves
                    The List interface solves the problem of needing a collection that maintains a specific
                    order of insertion and allows elements to be accessed or manipulated based on their position (index).

                    It permits duplicate elements (unlike Set).
                    It provides the contract for positional access, which the parent Collection interface does not.

            Important Methods:
                (Grouped by Behavior)

                Positional access:
                    1. E get(int index)                               //E means Type of elements
                    2. E set(int index, E element)
                    3. void add(int index, E element)
                    4. E remove(int index)

                Search operations:
                    5. int indexOf(Object o)
                    6. int lastIndexOf(Object o)

                Iterations:
                    7. ListIterator<E> listIterator()
                    8. ListIterator<E> listIterator(int index)

                Range view:
                    9. List<E> subList(int fromIndex, int toIndex)

                Java 8+ Default Methods (Behavioral Additions)
                   10. default void replaceAll(UnaryOperator<E> operator)
                   11. default void sort(Comparator<? super E> c)
                   12. default Spliterator<E> spliterator()


            Interview notes:
                   1. "What's the difference between Collection.add(E e) and List.add(int index, E e)?
                        The Collection method simply attempts to add the element (return value tells you if
                        it was successful).   The List method adds the element at a specified position,
                        which is a stronger guarantee and may incur $O(n)$ cost due to shifting elements.

                   2. "What makes List different from Set?
                        List allows duplicates and is ordered by index. Set does not allow duplicates and is not
                        ordered (unless a specialized Set like TreeSet is used).

                   3. ArrayList is fast for reads (get(index)) and additions to the end, but it is O(n) for
                      insertions/deletions in the middle. LinkedList is often better if middle modifications are frequent.


 5️⃣ AbstractList (Abstract Class):

        AbstractList is an abstract base class that provides a skeletal implementation of the List interface.
        It specifically helps implement random access lists (like ArrayList).

                                                             |==implements==> List(I)
            ArrayList and Vector ---extends---> AbstractList |---extends--> AbstractCollection ==implements==>Collection

        1. What problem the class solves
            The primary problem AbstractList solves is efficiently implementing the indexed methods of the List interface
            for collections that use a random access internal data structure (like an array).

               * It inherits generic collection methods from AbstractCollection.
               * It implements the List interface, providing implementation for index-based methods.
               * It adds default implementations for positional methods (add(index), remove(index), set(index),
                 indexOf, etc.) by relying on only two fundamental methods that must be implemented by the subclass:

                     1. E get(int index);
                     2. int size();

               * It handles the ListIterator logic and the internal structural modification count (modCount)
                 for fail-fast behavior.


        Key Note (The Optimization Strategy):
            While the default implementation for indexOf is O(n), the modification methods (add, set, remove)
            are not implemented here (they throw UnsupportedOperationException).
            This forces the concrete subclass (like ArrayList) to provide the necessary structure-specific
            O(n) shifting logic and to increment modCount when necessary.

        Interview notes:
             Question: "What is the key difference between AbstractList and AbstractSequentialList?"
                 AbstractList is optimized for Random Access structures (like arrays) by implementing methods based on get(index).
                 AbstractSequentialList is optimized for Sequential Access structures (like linked lists) by implementing
                 methods based on the ListIterator.

             Question: "What is the purpose of the modCount field in AbstractList?"
             Answer: It tracks structural modifications to the list (additions/deletions).
                     It is used by the list's Iterator to implement the fail-fast mechanism by throwing
                     a ConcurrentModificationException if the count changes unexpectedly during iteration.

        Misconception: AbstractList implements all the List methods.
        Correction: It implements the logic for many utility methods (indexOf, subList)
                     but throws UnsupportedOperationException for the crucial modification methods (add, set, remove),
                     forcing subclasses to provide the efficient, structure-specific implementation.



 6️⃣ AbstractSequentialList (Abstract Class):

        AbstractSequentialList is an abstract base class designed to minimize the effort required to implement
        the List interface for collections based on sequential access (like a linked list).

          * It is the direct base class for node-backed lists.

          LinkedList--extends-->AbstractSequentialList--extends-->AbstractList--extends-->AbstractCollection==implements==> Collection (I)

          * It extends AbstractList and which extends AbstractCollection, inheriting generic collection utilities.

        1. Core Purpose (The Problem it Solves)

            To provide an efficient skeletal implementation of the List interface for structures that rely on
            sequential access (like linked lists).

            It implements all indexed List methods (get(index), add(index), remove(index))
            by leveraging the list's ListIterator.

                example:
                            public E get(int index) {
                                    try {
                                        return listIterator(index).next();
                                    } catch (NoSuchElementException exc) {
                                        throw new IndexOutOfBoundsException("Index: "+index);
                                    }
                                }






 7️⃣ Set (Interface):

        The Set interface is a direct child of Collection and represents a  mathematical set: an unordered collection
        of elements that contains no duplicate elements.


        1. What problem the interface solves
            The Set interface solves the problem of needing a collection that guarantees uniqueness of its elements.
                * It enforces the fundamental contract that for any two elements e1 and e2 in the set,
                  e1.equals(e2) is always false.




                * It models the mathematical concept of a set, where the order of elements is irrelevant,
                  and membership is the only concern.
